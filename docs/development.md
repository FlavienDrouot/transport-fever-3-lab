# Development and deployment

The site is static HTML, CSS and native JavaScript modules, with no runtime dependencies or CDN. Node.js 22+ is required for tests and builds; Python 3 runs the basic local preview.

```sh
npm test
npm run build
npm run dev
```

Open http://127.0.0.1:4173. No `npm install` is needed. Serve over HTTP: opening `index.html` as a local file cannot load the modules and dataset. Refresh after edits; the preview has no automatic reload.

## Remote preview

When the checkout is on another computer, forward its loopback port:

```sh
ssh -N -L 4173:127.0.0.1:4173 user@development-host
```

Then open http://127.0.0.1:4173 on your computer. Stop the server and tunnel with Ctrl+C.

Alternatively, `npm run dev:remote` (also the Codex **Aperçu** action in `.codex/environments/environment.toml`) starts a private Tailscale Serve preview. Open the HTTPS URL printed in the terminal from a computer on the same tailnet. The launcher selects an available port starting at 8443, binds the server to loopback and relays only public site files. It does not use Funnel or change firewall rules.

Prerequisites: connected Tailscale CLI, MagicDNS/HTTPS certificates, Serve permissions and tailnet access rules allowing the chosen port. Keep the terminal open; Ctrl+C stops its server and Serve session. After forced termination, clean up only this preview's processes and relay; do not use `tailscale serve reset`, which affects other previews. For failures, inspect the terminal message, `tailscale status` and `tailscale serve status`. SSH forwarding remains an alternative.

## Navigation and experimentation

The three top-level spaces are **Compare**, **Design** and **Data & models**. Compare keeps **Race / Service** tabs visible in fixed positions. Race is rail-only: selecting it from Road switches to Rail. The **Rail / Road** selector lives in the comparison sidebar, alongside the vehicle and route settings. Design offers **Composition / Route**. Data & models offers **Catalogue / Models / Checks**; it owns long methods, inspiration and experimental observations. On desktop, contextual view links share the header with the three spaces; section anchors have no permanent third navigation row. Keep concise assumptions and chart help beside their controls. Legacy `#race`, `#economics`, `#trucks`, `#configurator` and `#route-profile` hashes, plus direct section hashes, continue to resolve to their view; computational modules and data fields retain their existing names.

A valid composition draft can enter Compare without saving, as a session-only vehicle; persistence still requires Save composition. The comparison’s composition action opens Design → Composition. Design → Route links directly back to Race or Service. Rail and Road always share one ordered route of one to 24 segments, at most 100 km total; one segment is the constant-grade/speed case. The final segment cannot be removed. Segment lengths are 0.01–100 km, grades −20% to +20%, speed limits 10–350 km/h. These transitions support rapid composition and route experiments. No automatic composition search or empty optimizer view is provided; revisit optimization when an agreed objective, constraints and validated solver are available.

## Deferred data and recovery

Startup loads `trains.json` for Race and Service. The first Road visit loads trucks, buses and trams; the first Composition visit loads the rail/tram components, powered trams and thumbnail index. Saved compositions trigger that configuration load in the background after startup so their definitions can be restored against the current catalogue. Successful dataset requests are reused across domains.

Data & models loads the inventory and experiments independently; motion checks use the already loaded trains. Road, Composition, inventory and experiments each show a local error and retry button on failure. Missing thumbnails leave the composition editor usable without images. Route/filter controls remain inert while their data loads; drawer close buttons stay available. A failure of the core train dataset still prevents startup. Revisit that dependency if an independent Road-only entry point is required.

The two comparison pickers use `src/vehicle-selector.js` for their entire search, order, count, action and row presentation. Domain adapters supply eligible vehicles, selected IDs and descriptive values. Pointer and keyboard identification use the same row event bindings. ## Acquire vehicle data from a Windows installation

`scripts/collect-game-vehicles.ps1` is an experimental, read-only source collector for Windows PowerShell 5.1 / PowerShell 7. It discovers TF3 in Steam libraries or accepts `-GamePath`. It writes a new ZIP to the Desktop (or an existing `-OutputDirectory`), containing vehicle `.mdl` definitions, `.mu.lua` formations, economy resources and selected metadata utilities from loose files or ZIP-compatible packs. It never runs game scripts or modifies the installation. Collected file size is limited to 2 MiB per resource and 32 MiB total; skipped resources and unreadable packs are listed in `manifest.json`. Original resource paths are preserved in the manifest rather than used as extraction destinations.

Run from Windows PowerShell in the directory containing the downloaded script:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\collect-game-vehicles.ps1
# Or provide the installation directory explicitly:
powershell -NoProfile -ExecutionPolicy Bypass -File .\collect-game-vehicles.ps1 -GamePath 'D:\SteamLibrary\steamapps\common\Transport Fever 3'
```

The execution-policy override applies only to this process. The collector has not yet been executed on a real TF3 installation or validated in PowerShell; a successful source collection is not a verified catalogue export. Unsupported packaging requires inspection of the actual installation or a documented in-game resource export. Keep collected game sources private and outside this repository. Do not publish them or overwrite the captured catalogues.

Evaluate metadata in the proper game context before importing: Lua expressions and automatic values (such as `-1` prices, maintenance and loading speed) cannot be treated as displayed values. Compare an exported locomotive and passenger/freight wagons against existing cards, verify units and difficulty, and retain model identifiers, game version and mods as provenance. The official [resource API](https://wiki.transportfever3.com/script-doc/api/res.html), [model metadata](https://wiki.transportfever3.com/doku.php?id=modding:general:resourcetypes:mdl) and [vehicle metadata](https://wiki.transportfever3.com/doku.php?id=modding:vehicles:basics) describe the starting points.

Retirement dates and active save modifiers are not applied.

Road and tram entries outside campaign content are all linked to their calculator/configurator records. All 43 captured railway wagon choices are matched too, covering the 41 standalone wagon resources plus the Swiss DPZ and British Mark 3 models stored with multiple units. Air/water and remaining internal railway components require separate checks before entering calculators. ### Reconcile captured names

`scripts/reconcile-catalogue-names.mjs` compares source metadata with the existing captured datasets and `data/vehicle-name-observations.json` (additional identity-only evidence). Costs are excluded from detailed-card matching because capture difficulty may differ. Condensed locomotive matching requires a unique agreement in year, speed, power and exact normal-scale purchase cost; mass, length and traction copied from source are never independent evidence. Condensed wagon matching requires year, speed, capacity and exact normal-scale purchase cost to agree, plus handling whenever present in source; candidates must be unpowered wagons with compatible cargo classes. Missing source handling is supplied by the capture (1899 universal freight wagon: 1×). Source IDs are kept; matching names and their capture references are recorded separately from runtime validation. Re-run reconciliation after importing a new export or correcting a card. `--details` emits candidate evidence to stdout for review; keep one-off results in the private work-vault or GitHub rather than the product repository.

For condensed-capture additions, `dataProvenance.observedFields` limits identity evidence to fields actually visible in the capture. Source-backed mass, traction and bounding-box length never count as independent confirmation. Stadler Citylink, Stadler TINA and the 2030 articulated freight tram use this path: five observed identity fields and an exact purchase-price check, with annual maintenance retained as a source-formula value.

Matching requires the same category and introduction year, compatible source cargo classes, and at least five concordant characteristics within display-rounding tolerances. Missing values provide no evidence. Source conversion capacity candidates are rounded per model before aggregation/matching, consistent with the detailed rail and road captures. Explicit cargo classes take precedence; absent bus classes imply passengers, and absent truck/tram classes can be inferred from exact `_box`, `_bulk`, `_stake` or `_tank` resource suffixes. This fallback never overrides contradictory explicit classes. Significant capacity, mass, speed, power or traction differences block an automatic association. Source bounding-box lengths and inferred per-car formation handling are secondary: differences are retained but may be accepted with at least five other concordant characteristics for model extents, or six for formation handling. A unique candidate is required; ties and conflicting captured names remain unresolved. The British Mark 3 is an explicit exception: its two documented internal resources must agree in every calculator fingerprint field and both costs, and must be the entire matching candidate set. They retain separate raw identities but one configurable choice. Additional duplicates or divergent physical properties invalidate that equivalence; the rule is not generalized to other ambiguous resources. Unmatched candidates, disagreements and provenance remain in the metadata JSON for maintenance, without per-row diagnostic disclosures in the public catalogue. Source and captured names remain searchable via their resource IDs and translation keys.

Multiple-unit candidates resolve every ordered component ID within its source directory before comparing aggregate physical characteristics; repeated cars are counted repeatedly. A matched formation name is not copied onto its component records. This aggregation is for identity evidence only: it does not validate coupling, purchase availability or calculator handling. Resolve those through in-game observations before promoting entries into calculators. Existing screenshot-confirmed names are retained.

## Custom compositions

The composition editor groups its name, Save composition and New composition controls in one wrapping toolbar, with carrier/category beside the heading. Vehicle cards keep quantity and reorder/remove actions on one row. On wide screens a wrapping flex layout gives the composition strip its explicit max-content width, capped at 45% of the form, and the totals fill the remaining width in as many columns as fit (130 px minimum). Cards have an explicit 180 px border-box width and minimum width, rather than only a flex basis, so intrinsic strip sizing accounts for their full width in Firefox as well. The strip keeps its natural card width; horizontal scrolling is reserved for compositions that exceed the available strip width. This prevents short compositions from reserving excessive width while a tall summary leaves blank space beneath them. Narrower screens stack the summary below. Empty status messages do not reserve a row. The current composition summary includes Power / mass in W/kg and Traction / mass in N/kg, using the aggregate empty mass of all components. These ratios use the composition's captured power and traction totals, without the calibrated motion-model multipliers, and update with quantities and component changes.

Design → Composition loads both acquired rail and tram adapters into the same composition builder. Carrier and transport category prevent mixing rail/tram or passenger/freight capacities. All freight selects general-purpose vehicles that can carry every freight type in Composition, Road and railway Freight Service. Specific freight-group filters also include these general-purpose components alongside the matching specialized vehicles. Specialized compositions require an explicit cargo group; incompatible specializations are rejected. Catalogue filters preserve ordered draft components. When adding to an empty draft or one containing only locomotives without passenger or freight capacity, the draft adopts the catalogue transport category and cargo group; existing locomotives are retained, and a nonempty draft cannot change carrier. Once capacity-bearing vehicles are present, the draft category and cargo context remain fixed and incompatible additions are rejected. New composition explicitly starts a draft in the selected catalogue context. The year filter can make a draft component unavailable without deleting it. Saved recipes keep ordered resource references and quantities; totals are recalculated, not persisted. The browser storage key is `tf3-compositions-v1`; definitions are limited to 100 compositions and 100 rows each, with 1–1,000 vehicles per row. Invalid, obsolete or incomplete definitions are skipped on restore. If storage is unavailable, compositions remain usable until reload and the save status explains this. Existing records can be edited or deleted; Data & models remains installation source data.

Rail passenger compositions join Race and Service. Rail freight compositions join Race and Freight Service; passenger and freight cohorts remain separate. Tram compositions join Road when Include trams and the year/category/cargo filters match; saving a tram sets those filters to its context. Road checkboxes determine both the current ranking and all phase diagrams; search only narrows the picker. Custom compositions use explicit aggregate handling and disable automatic recoupling. Freight Service compares delivery cost with train acceleration/braking, terminal/warehouse bonuses at each stop and loaded/empty returns. Saving a rail composition selects the matching economic category and cargo filter. The annual freight target counts deliveries across both legs when return is loaded, while passenger demand remains per direction. No default freight recipes are manufactured. All five economic axes dispatch through the same service model; freight and passenger rendering reuse the same charts and phase component. Actual in-game coupling restrictions and model-extent lengths retain the existing limitations.

Custom composition rows in the shared vehicle picker have a separate pencil button, outside the selection label, which opens the saved recipe in Design → Composition and focuses its name without changing selection. The same editor loader handles these shortcuts and the existing Edit/Duplicate actions. Saved recipes and route/service parameters are preserved.

### Live composition analysis

Design → Composition flows from vehicle catalogue to current composition, steady-running reference, grouped transient graph, route/service controls and selected-route results. Steady values and the Approach to steady running plot share one Steady running & transient phases disclosure, opened by default. Their explanatory text remains in a separate closed About this analysis disclosure inside it. Opening the group refreshes chart dimensions using the cached analysis. Route controls and selected-route results share one Route & service disclosure, opened by default, so they always expand or collapse together. Routine successful-status prose is omitted; exclusions still display their explanation. The steady reference uses the speed limit and signed gradient in each direction, averages cruising seconds per kilometre over the two legs internally and converts train maintenance using `GAME_YEAR_SECONDS`. Its displayed transport output replaces time/km with Rate × one-way distance for one train: passenger output is per direction (capacity·km/game year/direction); freight output counts all loaded legs (capacity·km/game year). With mean cruising seconds/km `t` and utilized capacity `C`, output is `C × GAME_YEAR_SECONDS / (2t)` for passengers and `C × (1 + loadedReturn) × GAME_YEAR_SECONDS / (2t)` for freight. A zero utilization gives zero output and an unavailable unit cost. Rate × distance has a one-sentence info tooltip explaining inverse Rate scaling with distance; the full measure, directional conventions and cruise-only assumptions remain under About this analysis. Unit cost uses the utilization setting and counts passenger journeys in both directions or freight deliveries on loaded legs, including the cost of an empty return. It excludes acceleration, braking, terminal handling and demand/frequency-driven fleet sizing; the selected-route results retain all of those effects. An uphill leg that cannot start gives no viable round-trip cruising reference.

The editor publishes its valid draft to `src/composition-analysis-controls.js` without saving it. The explicit comparison action adds a session-only version to the matching comparison catalogue; ordinary draft edits alone do not publish it. Route distance, rail gradient, infrastructure limit, utilization, demand, frequency, platform length and freight handling share the existing Rail Race/Service state. Selected-route service results use every shared route segment; the composition curves and steady reference retain uniform grade, preset speed cap and utilization settings. One segment supplies the reference grade; multiple segments retain the saved uniform reference grade. Demand is interpreted using the draft category: passengers per direction, or total freight deliveries. Custom compositions are never automatically coupled. Empty, incomplete or invalid drafts show only the invitation to add a powered vehicle and compatible capacity, hiding the analysis header, help, controls and results; invalid route fields keep the last valid settings and show an explicit notice. A platform or uphill-start exclusion explains why service results are unavailable. Platform limits and fleet constraints apply only to the selected-route summary: the steady reference and the chart describe one train at fixed selected utilization, with Rate and Frequency targets disabled. The curve reference uses uniform gradient, infrastructure limit, utilization, loaded return and freight handling settings. Route edits change the selected-route service result, without turning the composition curves into route-profile sweeps. A platform exclusion or incompatible rate target must not hide otherwise valid composition curves; an infeasible gradient still prevents round-trip curves.

`src/composition-analysis.js` reuses the Service engine for selected-route results and fixed-utilization composition curves. Opening Composition retains the shared route’s precision. The route summary links to Design → Route; selected-route service uses the segment sum and each segment’s gradient and speed limit. A single segment derives the uniform reference grade; with several segments the saved uniform grade is retained, and the reference cap remains a preset. The infrastructure limit and Frequency policy use segmented radio buttons; the policy sits alongside Target frequency and is disabled with that target. Results follow the shared terminology glossary.

Only the Approach to steady running graph is displayed. It plots peak service speed, `Rate × one-way distance / trainCount`, and `maintenancePerUnit / one-way distance` against total round-trip length. At zero gradient there is one peak-speed curve; with a nonzero signed gradient there are separate A→B and B→A curves with distinct colours and line styles, sharing one speed scale. Peak speeds include the braking constraint. Passenger Rate is per direction; freight Rate counts all loaded legs. Dividing cost by round-trip length instead would incorrectly halve the per-kilometre journey cost. An individual passenger return trip is not the cost denominator. Output rises and cost/km decreases towards the steady values above, independently of Rate, Frequency, frequency policy and platform constraints. At zero utilization, speed and zero output remain visible while cost is marked unavailable.

The display window is chosen by at most 32 fixed-utilization probes, doubling one-way distance until output reaches 99% of its steady reference and cost/km is at most 1% above its reference. It uses 81 logarithmically spaced samples starting at 10 m of total round-trip length (5 m one way), plus the exact selected distance when inside the domain, reusing cached service results. Distance and cost axes are logarithmic, explicitly labelled; speed and output remain linear. The logarithmic cost scale keeps high short-route costs from compressing the rest of the curve onto zero. Selected-route markers and inspection coordinates use total round-trip units. Longer routes retain their full-precision summary. Pointer movement and Left/Right/Home/End keys on the focused plot inspect sampled values; no separate slider is shown. The chart does not represent whole-fleet transitions; use selected-route service results for fleet sizing. Revisit this separation if a dedicated fleet optimizer needs a constraint-dependent sweep.
