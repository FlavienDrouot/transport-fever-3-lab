# Development and deployment

The site is static HTML, CSS and native JavaScript modules, with no runtime dependencies or CDN. Node.js 22+ is required for tests and builds; Python 3 runs the basic local preview.

```sh
npm test
npm run build
npm run dev
```

Open http://127.0.0.1:4173. No `npm install` is needed. Serve over HTTP: opening `index.html` as a local file cannot load the modules and dataset. Refresh after edits; the preview has no automatic reload.

## Remote preview

When the checkout is on another computer, forward its loopback port:

```sh
ssh -N -L 4173:127.0.0.1:4173 user@development-host
```

Then open http://127.0.0.1:4173 on your computer. Stop the server and tunnel with Ctrl+C.

Alternatively, `npm run dev:remote` (also the Codex **Aperçu** action in `.codex/environments/environment.toml`) starts a private Tailscale Serve preview. Open the HTTPS URL printed in the terminal from a computer on the same tailnet. The launcher selects an available port starting at 8443, binds the server to loopback and relays only public site files. It does not use Funnel or change firewall rules.

Prerequisites: connected Tailscale CLI, MagicDNS/HTTPS certificates, Serve permissions and tailnet access rules allowing the chosen port. Keep the terminal open; Ctrl+C stops its server and Serve session. After forced termination, clean up only this preview's processes and relay; do not use `tailscale serve reset`, which affects other previews. For failures, inspect the terminal message, `tailscale status` and `tailscale serve status`. SSH forwarding remains an alternative.

## Navigation and experimentation

The three top-level spaces are **Compare**, **Design** and **Data & models**. Compare keeps **Race / Service** tabs visible in fixed positions. A short question guide above Compare links, from simplest to most involved, to Race, Service, Composition and the Optimizer; **Hide guide** is remembered in this browser and **Guide** in the header shows it again. Race supports both Rail and Road, preserving the selected view when changing domain. Road uses the shared calibrated acceleration model; braking is omitted. The **Rail / Road** and shared **Passengers / Freight** selectors live together in the comparison sidebar. Design offers **Composition / Route / Optimizer**. Data & models offers **Catalogue / Models / Checks**; it owns long methods, inspiration and experimental observations. On desktop, contextual view links share the header with the three spaces; section anchors have no permanent third navigation row. Keep concise assumptions and chart help beside their controls. Mobile uses a sticky two-row header: brand, spaces and theme on the first row; contextual tabs and the drawer button on the second. Header height is measured by ResizeObserver for scroll offsets. The Support & contribute footer belongs to the main column, pushed to its bottom on short pages, and never spans beneath a desktop sidebar. Legacy `#race`, `#economics`, `#trucks`, `#configurator` and `#route-profile` hashes, plus direct section hashes, continue to resolve to their view; computational modules and data fields retain their existing names.

A valid composition draft can enter Compare without saving, as a session-only vehicle; persistence still requires Save composition. The comparison’s composition action opens Design → Composition. Design → Route links directly back to Race or Service. Rail and Road always share one ordered route of one to 24 segments, at most 100 km total; one segment is the constant-grade/speed case. The final segment cannot be removed. Segment lengths are 0.01–100 km, grades −20% to +20%, speed limits 10–350 km/h. Simple and Custom route settings are retained independently during the session and shared across domains and draft analysis. Opening the editor does not activate Custom; editing the geometry or any declaration (a changed route name does not count) or choosing Use this route does. These transitions support rapid composition and route experiments. Design → Optimizer starts with Ignore retirements checked and Stops & infrastructure expanded. It searches the selected Rail/Road domains for services meeting Rate, optional minimum/maximum Frequency intervals and Utilization; it minimizes fleet Running costs within explicit year/formation/fleet bounds. Route & infrastructure groups shared route settings and terminal access constraints separately from service goals. A list of reusable infrastructure uses progressive A/B, optional Rail/Road and station/platform toggles; unlisted stops need new terminals. Each declaration imposes reuse or an additional platform; existing upkeep is excluded, while permitted new installations, extensions and specialization upgrades count. The search sizes platforms and warehouses within user permissions, never infers shared-platform availability from Frequency. Rail results retain each feasible locomotive/MU model and the best three variants per wagon model (or complete-MU quantities), displayed in an always-visible comparison table below one selected-configuration card. The table initially shows five powered models; Show 5 more reveals five additional models once, then Show all reveals the remainder without rebuilding the selected card or expanded rows. Whole-row clicks expand powered-model/wagon rows or select leaf variants, with boxed chevrons and Expand/Collapse labels. Native buttons preserve keyboard access; explicit Select buttons choose a variant without expanding its row; selection preserves expanded rows and does not open a composition until the card action is used. The cheapest Rail service is selected by default. Road + Tram uses the same grouped table and selected card. Shared CSS subgrid rows align the headings, selected cards and table headings across domains on desktop; mobile stacks the domains independently. Fixed column widths keep both tables consistent, and the annual Running costs and Select columns stay pinned at the right of their horizontal scroll container. A visual header outside horizontal overflow sticks below the navigation during page scrolling, independently for each table; its horizontal position follows the original table. The original thead remains the accessible header, and the visual copy is hidden from assistive technology. Global API `best` is preserved; grouped opening uses the selected domain’s `groups` indexes. The locomotive quantity bound does not apply to repeated MUs, and MU + same-category wagon combinations are searched with identical-only coupling disabled, within train/terminal length and wagon-count bounds. Infrastructure inputs live outside the service form, so submission explicitly validates their enabled fields and opens enclosing disclosures on failure. The optimizer recap reuses the workspace sidebar column on desktop, filling the viewport below the header with independent scrolling. On mobile it moves into the optimizer layout as a compact disclosure. Industry endpoints automatically supply free specialized Truck terminals. Road trams require separate reusable platforms or new stations within the normal bounds and tariffs; `tramOnly` alternatives keep these facilities separate from the built-in Truck terminals. Rail platform length maxima default to 840 m and cannot exceed this game maximum; enabling infrastructure hides the separate train-length input and uses physical limits within the game platform maximum of 840 m.

## Chart axes

Linear chart axes label round values from `src/scales.js`: `roundTicks` picks the 1, 2 or 5 × 10ⁿ step closest to the requested interval count, `boundedTicks` keeps both meaningful ends of a distance or year study with round values between them, and `timeTicks` steps clock axes in 5 s to 2 h units (0:30, 1:00, 5:00…). Logarithmic axes keep 1/2/5 ticks per decade. Below 700 px, `src/chart-toolbar.js` adds a **Chart options** button to each chart toolbar; Linear/Log switches (`fieldset[id$="-scale"]`) and exports stay hidden until it is opened, while view switches such as Time/Distance remain visible. Rail and Road Service both draw **Running cost over distance** with `renderEconomicChart`; Road passes its own `costAt` and extends ∞ like Rail, to the later of the last leader change and the distance where every vehicle cruises. The ranking at cruising speed uses the same table in Rail and Road; Steady speed and Utilization sit behind **Show calculation details**.

## Saved routes and expected service

`src/route-plan.js` owns the versioned route/service declaration and pure flow arithmetic. `src/route-plan-controls.js` mounts the declaration around the line map in Design → Route (`layout` slots: the name, library and loads above the map, the details panel and checklist below it). The loads are Passengers or Freight, then each good with its type. The service lanes (`lanes`) are drawn by the line map under its SVG, from the same horizontal positions: each stop sits under its map marker, the A → B and B → A rows carry its trip legs, flow bands span the sections between stops, and `＋ stop` marks the free boundaries. A stop too narrow for its trips shows a count that opens it. Map stops are buttons too. One details panel serves the whole line: a segment (the geometry inspector, then its existing tracks and roads), a stop (trips there, buildings, infrastructure) or a trip (good, from, to, Rate, same in the other direction, buildings); closing a stop or trip returns to the selected segment. Without `layout`, the control keeps its standalone grid with stops in columns. Each cell lists the trip legs boarding (⬆ to …) or alighting (⬇ from …) there; a chip opens its trip, and ＋ adds a trip starting there. Every choice is a native radio group styled as buttons; numbers and names stay inputs. Flow bands come from `terminusFlows`. A checklist built from `declarationReport` and the flow warnings replaces the former summary paragraph. Until a load category is chosen, the Passengers/Freight selector is highlighted and a grid ＋ points back to it. Buildings and infrastructure entries collapse to a one-line summary; a new entry opens in edit mode and **Done** collapses it once its inputs are valid. Radio changes redraw the editor and restore focus; typed names and numbers redraw only the grid and checklist. A definition stores geometry, one infrastructure record per segment, named stops at segment boundaries, user-named goods with stable IDs, directional freight operations referencing local building IDs, industry recipe ratios, input/output storage and existing stop infrastructure. Each stop can serve up to 20 named buildings; stock and recipes are owned by those buildings while stations/platforms remain attached to the physical stop. No vehicle metadata, compartments or cached simulation totals are stored. New Industry stock rows use the shared 800-capacity output-storage planning default; the input default remains 100 and explicit saved capacities are preserved.

Route definitions use schema version 5. Version 5 stores each building's storage as `{cargoId, side, capacity}`: an Industry chooses `input` or `output` per good, an industrial building only `input` (any whole limit), and warehouses and unspecified buildings have none. `storageByRole` migrates earlier input/output pairs, keeping the output capacity where that building loads the good (or its recipe outputs it) and the input capacity otherwise. As in version 4, `trips` declare the service and `validateRoutePlan` derives each stop's `operations` (annual load at the start, unload at the end, both ways when `bothWays`), so `routePlanFlows`, the recipe arithmetic and `route-plan-service.js` read operations as before; stored operations of a version 4 definition are ignored and re-derived. Version 3 definitions migrate through `tripsFromOperations` (proportional unloading of the parcels onboard, terminus delivery, deterministic `trip:migrated-n` IDs, per-visit quantities dropped). Loads keep the version 3 rules: each load has a `type` among `LOAD_TYPES` (`passengers`, `general`, `bulk`, `goods`, `flatbed`, `liquid`; `general` maps to the `all` cargo filter, i.e. general-purpose vehicles), or `null` for a version 2 good awaiting a choice. Validation rejects mixing passengers with freight, a second passenger load, and storage or recipes on passengers. Version 1 single-building definitions are validated and migrated on load (then to version 3), retaining explicit capacities and assigning existing operations to the migrated building. IDs used by an operation must identify a building at that same stop (or be null for an unspecified building). The UI refuses to remove a referenced building until its operations are reassigned or removed. Recipe requirements aggregate only moves attributed to their owning Industry. The browser library retains its version 1 envelope/key `tf3-routes-v1`, with an explicit Save/Update, Duplicate draft, Load and Remove saved route workflow. Reload restores the library, not an automatically activated route. Definitions are validated individually; malformed records are skipped while valid routes remain available, with a visible warning. The library is bounded at 100 routes and four million serialized characters. Unavailable/quota-blocked storage keeps the library in memory and explicitly reports session-only persistence, including when removing an entry. No backend, account or synchronization is introduced.

The geometry controller calls `beforeChange` with the proposed segments and structural edit before mutation. Stops remain attached to the following segment on insertion/deletion; removing a connecting segment that would merge stops is rejected. Reordering geometry keeps stop order but moves the segment's declared infrastructure with it. `setStops` adds named markers and accessible labels to the profile sketch; the segment panel's map link reuses `selectSegment`. Loading restores geometry and all declarations together and activates Custom route. Optimizer tier changes retain the same segment structure and preserve declarations.

`routePlanFlows` keeps per-visit (legacy only) and annual quantities separate. Unloading occurs before loading, percentage operations use that load at the operation, and residual freight carries into the return direction; `terminusFlows` in `route-plan-service.js` adds the delivery at B that the calculators and the Route summary use. Recipe requirements derive from the planned loaded outputs, using shared production cycles for joint outputs. The editor reports inconsistent unloading and uninitialized percentage loading without claiming vehicle or production feasibility. Tests cover arithmetic, multiple outputs, input-free sources, corrupt persistence, safe stop labels, physical infrastructure limits and geometry changes.

`src/route-plan-service.js` maps a validated plan onto inputs the engines already accept, without simulating anything: `declaredRouteProfile` (tier speed ceilings, tracks, lanes, Tram access and City flag on the stored segments), `declaredService` (category, one good per direction with its annual Rate, freight group — `all` when the two groups differ —, the Rate per direction on the busiest section, the return share and, with intermediate stops, the `servicePattern`, or the reasons it is unsupported) and `declaredServiceText`, `declaredEndpointModel` (endpoint sites and reusable terminals in the Optimizer's own shape), `uncappedDeclaredTiers` (restores the stored speeds so the Optimizer can upgrade declared tiers when route Running costs count), `declaredPlatformLength`, `declaredHandling` (specialized terminals, and warehouses specialized for the service good through `warehouseSpecializedFor`), `declaredServiceInputs` and `declarationReport` (what each view uses and skips). `optimizerInfrastructureValue` in `src/optimizer-infrastructure.js` turns sites, entries and new-terminal bounds into the `infrastructure` request for both the manual controls and the declaration, so the two cannot drift. `src/app.js` keeps the plan next to the route selection: `currentRoute()` overlays the declaration on the stored custom segments (never on the Simple route) and feeds `railRouteProfile`, the Optimizer and the status line; `applyDeclaredCategory()` switches Compare (and asks the Optimizer to `followDeclaration()`) on view changes, custom-route activation and declaration edits; `syncDeclaredLocks()` writes the declared Rate, cargo group, Loaded return, Maximum train length and specialized terminals into the Rail Service, Road Service and Composition controls, makes them `inert` and restores their previous values when the declaration stops applying. The Optimizer takes `getPlan` and replaces the manual Rate, Loaded return, per-segment tracks/lanes/Tram choices, endpoint buildings and reusable entries (kept untouched meanwhile) with the declared ones; line-control edits and opened proposals go through `mergeUndeclaredLineChoices` / `withoutDeclaredLineChoices` so declared values are never copied into the stored geometry. Any change to goods, stops or segment infrastructure activates the custom route at once (`declarationEdited`) and otherwise resynchronizes the analyses after a 150 ms debounce; a name change does not. `declaredService` evaluates `terminusFlows`, i.e. `routePlanFlows` on the plan plus a synthetic 100% unload at B, so the outbound load is what leaves A and the return load only what the return direction loads; `routePlanFlows` itself is unchanged. `infrastructure.countRunningCosts` (default true) separates constraints from costs: false keeps `optimizerTerminalChoices` and storage checks, skips the cost pruning, leaves stop costs out of `cost`/`unitCost` and keeps them as `uncountedTerminalRunningCosts`, a tie-break in `compareOptimizerResults`. The Optimizer infrastructure control sends the infrastructure request whenever the checkbox is checked or a declaration applies. Tests in `tests/route-plan-service.test.js` cover each adapter, the shared infrastructure builder and an end-to-end Optimizer evaluation. `lineInfrastructure.existing` (validated per segment in `optimizer-line-infrastructure.js`) makes `segmentLineTiers` offer the existing tier for free and faster tiers for the maintenance difference; `railTrackMaintenance` prices existing tracks by their upgrade and additional tracks in full, and `sizeRailLineTracks` reuses it. `loadedReturn` accepts `false`, `true` or a share between 0 and 1 (`returnShare` in `service-fleet.js`): the lighter leg's load as a share of the busier one. Rail, Road, tram bounds and the Optimizer's delivery bounds scale return handling and deliveries by it; declared shares travel through Compare checkboxes as `data-share` (`loadedReturnValue`). Unsupported declarations (several goods in one direction, return-only flows, ambiguous buildings, recipes) are reported by `declarationReport`, never guessed; add the model support first, then the adapter.

## Acquire vehicle data from a Windows installation

`scripts/collect-game-vehicles.ps1` is an experimental, read-only source collector for Windows PowerShell 5.1 / PowerShell 7. It discovers TF3 in Steam libraries or accepts `-GamePath`. It writes a new ZIP to the Desktop (or an existing `-OutputDirectory`), containing vehicle `.mdl` definitions, `.mu.lua` formations, economy resources and selected metadata utilities from loose files or ZIP-compatible packs. It never runs game scripts or modifies the installation. Collected file size is limited to 2 MiB per resource and 32 MiB total; skipped resources and unreadable packs are listed in `manifest.json`. Original resource paths are preserved in the manifest rather than used as extraction destinations.

Run from Windows PowerShell in the directory containing the downloaded script:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\collect-game-vehicles.ps1
# Or provide the installation directory explicitly:
powershell -NoProfile -ExecutionPolicy Bypass -File .\collect-game-vehicles.ps1 -GamePath 'D:\SteamLibrary\steamapps\common\Transport Fever 3'
```

The execution-policy override applies only to this process. The collector has not yet been executed on a real TF3 installation or validated in PowerShell; a successful source collection is not a verified catalogue export. Unsupported packaging requires inspection of the actual installation or a documented in-game resource export. Keep collected game sources private and outside this repository. Do not publish them or overwrite the captured catalogues.

Evaluate metadata in the proper game context before importing: Lua expressions and automatic values (such as `-1` prices, maintenance and loading speed) cannot be treated as displayed values. Compare an exported locomotive and passenger/freight wagons against existing cards, verify units and difficulty, and retain model identifiers, game version and mods as provenance. The official [resource API](https://wiki.transportfever3.com/script-doc/api/res.html), [model metadata](https://wiki.transportfever3.com/doku.php?id=modding:general:resourcetypes:mdl) and [vehicle metadata](https://wiki.transportfever3.com/doku.php?id=modding:vehicles:basics) describe the starting points.

### Reconcile captured names

`scripts/reconcile-catalogue-names.mjs` compares source metadata with the existing captured datasets and `data/vehicle-name-observations.json` (additional identity-only evidence). Costs are excluded from detailed-card matching because capture difficulty may differ. Condensed locomotive matching requires a unique agreement in year, speed, power and exact normal-scale purchase cost; mass, length and traction copied from source are never independent evidence. Condensed wagon matching requires year, speed, capacity and exact normal-scale purchase cost to agree, plus handling whenever present in source; candidates must be unpowered wagons with compatible cargo classes. Missing source handling is supplied by the capture (1899 universal freight wagon: 1×). Source IDs are kept; matching names and their capture references are recorded separately from runtime validation. Re-run reconciliation and `node scripts/import-vehicle-availability.mjs` after importing a new export or correcting a card. The availability importer resolves explicit provenance/reconciled IDs, expands formations, checks equivalent-model agreement, and writes the compact `data/vehicle-availability.json` index for all selectable railway/Road/tram records and tram components. It never guesses matches from labels or alters captured introductions. `--details` emits candidate evidence to stdout for review; keep one-off results in the private work-vault or GitHub rather than the product repository.

For condensed-capture additions, `dataProvenance.observedFields` limits identity evidence to fields actually visible in the capture. Source-backed mass, traction and bounding-box length never count as independent confirmation. Stadler Citylink, Stadler TINA and the 2030 articulated freight tram use this path: five observed identity fields and an exact purchase-price check, with annual maintenance retained as a source-formula value.

Matching requires the same category and introduction year, compatible source cargo classes, and at least five concordant characteristics within display-rounding tolerances. Missing values provide no evidence. Source conversion capacity candidates are rounded per model before aggregation/matching, consistent with the detailed rail and road captures. Explicit cargo classes take precedence; absent bus classes imply passengers, and absent truck/tram classes can be inferred from exact `_box`, `_bulk`, `_stake` or `_tank` resource suffixes. This fallback never overrides contradictory explicit classes. Significant capacity, mass, speed, power or traction differences block an automatic association. Source bounding-box lengths and inferred per-car formation handling are secondary: differences are retained but may be accepted with at least five other concordant characteristics for model extents, or six for formation handling. A unique candidate is required; ties and conflicting captured names remain unresolved. The British Mark 3 is an explicit exception: its two documented internal resources must agree in every calculator fingerprint field and both costs, and must be the entire matching candidate set. They retain separate raw identities but one configurable choice. Additional duplicates or divergent physical properties invalidate that equivalence; the rule is not generalized to other ambiguous resources. Unmatched candidates, disagreements and provenance remain in the metadata JSON for maintenance, without per-row diagnostic disclosures in the public catalogue. Source and captured names remain searchable via their resource IDs and translation keys.

Multiple-unit candidates resolve every ordered component ID within its source directory before comparing aggregate physical characteristics; repeated cars are counted repeatedly. A matched formation name is not copied onto its component records. This aggregation is for identity evidence only: it does not validate coupling, purchase availability or calculator handling. Resolve those through in-game observations before promoting entries into calculators. Existing screenshot-confirmed names are retained.

`npm run build` precalculates the default Optimizer request and writes a small `data/optimizer-default.json` manifest plus a versioned result asset in `dist/data`. The manifest is revalidated before use; the result asset can stay in the browser’s HTTP cache. A canonical SHA-256 key checks every request parameter and the loaded catalogue. Asset URLs also hash all current `src/*.js`, so each build automatically invalidates older model results without a manual model version. Only the initial default request uses this cache, and missing/offline/incompatible cache data falls back to the normal Worker; cancellation and edits during loading discard the pending cache answer. For a development preview, run `npm run cache:optimizer` to generate ignored cache files in `data/`; regenerate after source/data changes, or remove those generated files to test the Worker fallback. The build excludes these development artifacts and always regenerates its own answer.
